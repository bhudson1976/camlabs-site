Rule-Based vs ML-Based Redaction Engines: Which Is Safer?

By CamLabs AI
November 13, 2026 · 5 min read

When you pick a redaction tool, you’re implicitly choosing a detection strategy. Rule-based engines match patterns. ML-based engines read context. Each approach has real strengths — and real failure modes. Knowing the difference helps you choose the right tool for the job and understand what to verify before you send a document.

How rule-based redaction works

A rule-based engine looks for text that matches a known pattern. Social Security numbers, for example, follow the format XXX-XX-XXXX — three digits, a dash, two digits, a dash, four digits. The engine encodes that pattern as a regular expression and scans the document for every match.

The same approach covers most structured PII: credit card numbers follow the Luhn algorithm and standard grouping patterns; phone numbers match a handful of North American and international formats; dates of birth, email addresses, and driver’s license numbers each have recognizable shapes. For this category of data, rule-based detection is fast, deterministic, and auditable — you can inspect exactly what pattern fired on exactly what text.

The key strengths:

  • Predictable. The same input always produces the same output. There is no probability score, no model drift, and no threshold to tune. If the text matches the pattern, it is flagged.
  • No false positives on exact matches. A regex for XXX-XX-XXXX will not accidentally flag a person’s name. The match either fits the format or it doesn’t.
  • Lightweight and on-device friendly. Pattern matching requires no large model files, no GPU, and no network connection. It runs quickly even on older hardware.
  • Easy to audit. A compliance review can inspect the pattern library and confirm that every SSN format is covered. There is no black-box model to explain.

The key limitation: rule-based engines can only detect what has a known format. A person’s name in running text — “John Smith signed the agreement” — has no reliable pattern. Neither does a job title, a medical diagnosis, or a free-text description of a location. For unstructured PII that relies on meaning rather than format, rules alone are not enough.

How ML-based (NER) redaction works

Machine-learning approaches to PII detection typically use Named Entity Recognition (NER) — a type of model trained to label spans of text with categories like PERSON, ORG, DATE, or LOCATION. Rather than matching a fixed pattern, a NER model reads the sentence around a word and predicts what kind of entity it is based on context.

This unlocks detection of things rules can’t reach: a person’s name in a letter, a company name in a contract, an informal address written as a paragraph rather than a standard postal format.

The key strengths:

  • Context-aware. “Apple” might be a company or a fruit; a NER model can usually tell from context. Rules cannot.
  • Covers unstructured PII. Names, organizations, and free-text locations are within reach without maintaining an exhaustive list of every possible value.
  • Handles variation. A model trained on many address formats may generalize to formats that a rule set hasn’t anticipated.

The key limitations are significant for high-stakes redaction work:

  • Probabilistic, not deterministic. Every prediction carries a confidence score below 100%. The model can miss entities (false negatives) or flag text that isn’t sensitive (false positives). Both types of error are possible in the same document.
  • Hallucination risk. Large language models used for PII extraction can occasionally identify entities that are not present in the document at all. This is rare but non-zero, and it is difficult to audit systematically.
  • Harder to audit. When a model misses a name, it is not easy to explain why or guarantee it won’t happen again on a similar document. Rule sets can be patched; models must be retrained or fine-tuned.
  • Heavier infrastructure. NER models require more memory and compute than pattern matching. On-device deployment is possible — several capable models are small enough to run locally — but the resource requirement is higher, and cloud-based NER services require sending your documents off-device.
  • Training data dependency. A model is only as good as what it was trained on. Unusual document formats, specialized domains (medical, legal, financial), or non-English text may perform worse than the benchmark numbers suggest.

The hybrid approach

In practice, most serious redaction pipelines use both. The common pattern is straightforward: use rules for structured data where format is known and reliability is paramount, and use ML for unstructured text where context matters.

A hybrid engine might apply regex patterns to catch every SSN, card number, and phone number with high confidence, then run a NER pass to surface names and organizations that have no fixed format. The results of both passes are surfaced for human review before anything is permanently removed.

Human review remains important in either case. Even a perfect rule set can miss an SSN handwritten in an unusual format or split across a line break. Even a strong NER model can miss a name it has not encountered before. The safety net is a reviewer who checks the results before the redactions are applied.

Privacy implications: on-device vs cloud

The choice of detection strategy intersects with where the processing happens.

Rule-based engines have a natural fit for on-device processing. The pattern library is a small file; the matching logic is minimal code. There is no reason to send a document to a server just to run a regex.

ML models can also run on-device, but the tradeoff changes. A capable NER model might be tens to hundreds of megabytes. It runs on-device without sending data anywhere, but it requires more storage and may be slower on low-end hardware. Cloud-based NER services shift that compute cost off the device — but then your document leaves the device entirely, which raises its own compliance questions for sensitive documents.

For documents containing financial records, medical information, legal exhibits, or other regulated data, on-device processing is often the only defensible choice regardless of detection approach.
