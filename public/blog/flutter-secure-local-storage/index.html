Is SharedPreferences Secure? The Flutter Storage Mistake That Leaks Tokens

By Bryon Hudson · Founder, CamLabs
June 25, 2026 · 5 min read

Of all the security mistakes I see Flutter developers make, this is the most common — and the most quietly dangerous, because it feels safe. It's storing sensitive data on the device and assuming that "on the device" means "protected." It doesn't.

The short version: no, SharedPreferences is not secure. If you're keeping auth tokens, session JWTs, or personal data in it, you're storing them in plaintext on disk — and "it never leaves the device" is solving the wrong half of the problem.

Why "It Never Leaves the Device" Misses the Point

Keeping data local protects it in transit — it's not flying across the network to be intercepted. Good. But security has a second half: data at rest. The device itself is not a sealed vault. It's an environment other things can read:

  • On desktop (Windows & macOS): your app writes its data to a user-readable application-support folder. Any process running as that user — or anyone who walks off with the laptop — can open those files.
  • On mobile: a rooted or jailbroken device exposes your app's sandbox completely, and backups can carry that plaintext off the phone entirely.
  • Everywhere: "local" never meant "encrypted." It just meant "didn't get uploaded."

What SharedPreferences Actually Is

Under the hood, SharedPreferences (and similar default stores) is just a plaintext file — XML, a plist, or JSON depending on the platform. There's no encryption. Open the file, read the values. The same goes for an unencrypted sqflite or Hive database, or a config file you wrote "just to cache the token." If a human can read the file, so can an attacker who gets to it.

What Gets Leaked This Way

  • Auth tokens & JWTs — the single most common item, and a stolen session is a logged-in attacker.
  • Personal data (PII) — cached user profiles and API responses that are now sitting in cleartext.
  • API keys you cached at runtime — same exposure as hardcoding them, just written later.

How to Store Sensitive Data Correctly

  • Use platform-backed secure storage. flutter_secure_storage hands your secrets to the OS's real vault — Keychain on macOS/iOS, Keystore on Android, DPAPI/credential locker on Windows. That's the right home for tokens and keys.
  • Encrypt databases at rest. If you persist sensitive records, encrypt the store (e.g. SQLCipher, or an encrypted Hive box) — and keep the encryption key itself in secure storage, not next to the data.
  • Don't store what you don't need. Prefer short-lived access tokens with refresh flows over long-lived secrets sitting on disk for months. The safest data is the data you never persisted.

The Catch: You Have to Actually Catch It

Here's why this one is so persistent — it never throws an error. SharedPreferences works perfectly; the app runs, the token saves, the feature ships. Nothing tells you it's insecure, so a manual code review has to remember to look for it, on every build, forever. That's exactly the kind of silent, easy-to-miss pattern an automated audit is built to flag — pointing you at the file and line where a sensitive value is going somewhere it shouldn't, before it ever reaches a user's disk.

The Bottom Line

"Local-first" is a philosophy I believe in deeply — but local-first means keeping data on your terms, not leaving it unlocked because it happens to sit on a hard drive. Treat the device as a place that needs protecting too, store secrets in the vault the OS already gives you, and verify it on every build.
